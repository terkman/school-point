# คู่มือปฏิบัติการ: เตรียมรีเซ็ตข้อมูลคะแนน

เอกสารนี้เป็นแผนปฏิบัติการและจุดตัดสินใจเท่านั้น **ไม่ใช่สคริปต์ล้างข้อมูล**
และห้ามใช้แทนการอนุมัติจากผู้รับผิดชอบข้อมูลของโรงเรียน

## ข้อสรุปที่แนะนำ

คำว่า “ล้างคะแนนและเริ่มใหม่ แต่เก็บชื่อนักเรียน/บุคลากร” มีความหมายที่ต่างกัน
มาก 2 แบบ:

| ทางเลือก | ผลลัพธ์ | คำแนะนำ |
| --- | --- | --- |
| **A. เริ่มภาคเรียนใหม่เชิงปฏิบัติการ (แนะนำ)** | เก็บตัวตน บัญชีเข้าใช้ รายชื่อ ห้องเรียน/การลงทะเบียน การมอบหมายครู กฎคะแนน สิทธิ์ และประวัติ audit ไว้; สร้างบัญชีคะแนนของภาคเรียนใหม่ที่ 100 คะแนน และเก็บประวัติภาคเรียนเดิมตามนโยบาย | ใช้เป็นค่าเริ่มต้น |
| **B. ล้างเฉพาะข้อมูลปฏิบัติการของขอบเขตที่เลือก** | อาจต้องเก็บถาวรหรือส่งออกก่อน แล้วจึงล้างข้อมูลคะแนน/คำขอ/เหตุการณ์/เวิร์กโฟลว์ของภาคเรียนที่ระบุ | ทำได้เฉพาะเมื่อเลือกขอบเขตการเก็บรักษาและอนุมัติเป็นลายลักษณ์อักษรแล้ว |
| **C. “เหลือเพียงชื่อ” ตามตัวอักษร** | จะลบบัญชีเข้าใช้ รหัสประจำตัว ความสัมพันธ์นักเรียน–ห้อง–ภาคเรียน ครูประจำชั้น กฎ คะแนน สิทธิ์ เอกสาร และประวัติ ทำให้ระบบใช้งานต่อไม่ได้แม้ชื่อยังอยู่ | ไม่แนะนำ; เป็นการสร้างฐานข้อมูลใหม่/นำเข้าข้อมูลใหม่ ไม่ใช่การรีเซ็ตงานประจำ |

ระบบมี `public.initialize_term_scores(p_term_id)` สำหรับสร้างบัญชีคะแนนของนักเรียนที่
ลงทะเบียนในภาคเรียนที่ `planned` หรือ `active` โดยเริ่มที่ 100 และสร้างรายการ
`semester_opening` ตามการออกแบบแบบ append-only อยู่แล้ว จึงควรใช้กระบวนการเปิด
ภาคเรียนใหม่แทนการแก้ยอดหรือการลบประวัติภาคเรียนเดิมโดยตรง

## ขอบเขตที่ต้องรักษาไว้สำหรับทางเลือก A

ห้ามลบหรือแก้ไขระหว่างการเริ่มภาคเรียนใหม่:

- ตัวตนและการเข้าใช้: `auth.users`, `public.profiles`, `public.students`,
  `public.teachers`, `private.login_identities`, `private.account_activations`,
  `private.student_private_identities`, `private.student_guardian_contacts`,
  `private.account_provisioning_queue` และรูปประจำตัวใน storage bucket
  `student-profile-images`
- โครงสร้างและรายชื่อ: `public.academic_terms`, `public.classrooms`,
  `public.enrollments`, `public.teacher_classroom_assignments`
- การตั้งค่า/สิทธิ์: `public.behavior_rules`, `public.positive_behavior_rules`,
  `public.staff_permission_grants`, `public.staff_permission_grant_classrooms`
- หลักฐานการกำกับดูแล: `public.audit_logs`, `private.import_batches` และข้อมูล
  ยืนยันอื่นที่นโยบายโรงเรียนกำหนดให้เก็บ

หมายเหตุ: หากเปิดภาคเรียนใหม่ จำเป็นต้องตรวจและสร้าง/คัดลอกห้องเรียน การลงทะเบียน
และการมอบหมายครูของ **ภาคเรียนใหม่** ก่อนเรียกการเริ่มคะแนน ระบบไม่ควรเดา
ความสัมพันธ์ข้ามภาคเรียนแทนผู้ดูแลข้อมูล

## รายการข้อมูลปฏิบัติการที่ต้องตัดสินใจเรื่องการเก็บรักษา

ตารางต่อไปนี้เป็น “ผู้สมัคร” สำหรับการนับและกำหนดแผน retention ใน
`supabase/operations/preview_operational_reset.sql` ไม่ได้หมายความว่าอนุญาตให้ลบ:

| กลุ่ม | ตาราง | การพิจารณา |
| --- | --- | --- |
| ยอดและสมุดรายการ | `public.score_accounts`, `public.score_ledger` | ยอดของภาคเรียนใหม่ควรเป็น 100 จาก RPC; `score_ledger` มี trigger ป้องกันการแก้/ลบ จึงควรเก็บหรือ archive ก่อนเสมอ |
| เหตุการณ์และคำขอ | `public.incidents`, `public.point_addition_requests`, `public.deduction_approval_requests`, `public.appeals` | อาจมีข้อมูลส่วนบุคคล/ข้อโต้แย้งและการอุทธรณ์ จึงต้องมี retention owner ระบุชัดเจน |
| งานติดตาม | `public.follow_up_cases`, `public.guardian_contact_tasks`, `private.guardian_contact_attempts` | เคสที่ยังเปิดอยู่ต้องมีผู้รับผิดชอบตัดสินใจว่าจะ carry-over, ปิดตามขั้นตอน, หรือ archive; ห้ามลบทิ้งเพื่อให้ตัวนับเป็นศูนย์ |
| กลุ่มคำสั่งแบบ bulk | `private.deduction_batches`, `private.addition_batches` | เป็นหลักฐาน idempotency และ roster ที่คัดเลือก; ควรเก็บพร้อมรายการลูกที่อ้างถึง |
| ผลพิจารณาอุทธรณ์ | `private.appeal_decisions` | เป็นประวัติ immutable; เก็บร่วมกับ `public.appeals` |
| เอกสารกระดาษ | `public.student_paper_documents`, `public.student_paper_document_events`, `public.paper_documents`, `public.paper_document_events` | มีสองชุดตารางเอกสารใน schema ปัจจุบันและทั้งคู่เชื่อมกับเหตุการณ์/อุทธรณ์; ต้อง archive เป็นชุดพร้อม event |
| ไฟล์หลักฐาน | `storage.objects` เฉพาะ bucket `score-evidence` | นับและส่งออก/กำหนด retention แยกจากแถวฐานข้อมูล; ห้ามลบรูปโปรไฟล์ |

`public.audit_logs` ไม่อยู่ในรายการล้างของแผนแนะนำ เพราะเป็น audit trail แบบ
immutable และมีทั้งเหตุการณ์คะแนนและการจัดการบัญชี/รายชื่อปะปนกัน

## ลำดับงานที่ปลอดภัย

1. หยุดการเขียนชั่วคราวในช่วงปฏิบัติการ: แจ้งผู้ใช้, ปิดงานอัตโนมัติ/Edge Function
   ที่เขียนข้อมูลถ้ามี, และกำหนดผู้รับผิดชอบช่วงเวลาการเปลี่ยนผ่าน ห้ามทำในช่วงที่
   ครูยังบันทึกเหตุการณ์หรือแอดมินกำลังอนุมัติคำขอ
2. รันเฉพาะการอ่าน `supabase/operations/preview_operational_reset.sql` ด้วยสิทธิ์
   ผู้ดูแลที่ใช้สำหรับตรวจสอบ และบันทึกผลลัพธ์/เวลา/ชื่อโครงการไว้ใน ticket การเปลี่ยนแปลง
3. เลือกขอบเขตและเจ้าของ retention เป็นลายลักษณ์อักษร: ระบุ `term_id` หรือช่วงเวลา,
   ตารางในแต่ละกลุ่ม, ระยะเวลาเก็บ, ตำแหน่งสำรอง, ผู้อนุมัติ และวิธีดูข้อมูลย้อนหลัง
4. สร้าง backup ที่กู้คืนได้: ใช้ snapshot/backup ของโครงการที่รองรับการกู้คืน พร้อม
   export ข้อมูลในขอบเขตและไฟล์ `score-evidence` ที่ตรวจด้วย checksum; บันทึก migration
   version, เวลา UTC, row counts ก่อนดำเนินการ และทดสอบการกู้คืนในสภาพแวดล้อมแยก
5. ตรวจ preconditions: ไม่มีการนำเข้าหรือการเขียนค้าง, ตรวจรายการเคส/งานติดต่อที่ยัง
   `open`/`following_up`/`pending`, ตรวจคำขอและอุทธรณ์ที่ยังรอ, และตรวจจำนวนบัญชีคะแนน
   ของภาคเรียนเป้าหมายเทียบกับ enrollment ที่ active
6. **จุดยืนยันก่อนทำการเปลี่ยนแปลง:** ผู้ดูแลข้อมูล, ผู้มีอำนาจด้านวินัย/กฎหมาย, และ
   ผู้ปฏิบัติการต้องยืนยันร่วมกันว่าเลือก A หรือ B, ขอบเขต `term_id`, แผน retention,
   backup ID, วิธี rollback, และช่วงหยุดเขียนแล้ว หยุดทันทีหากขาดข้อใดข้อหนึ่ง
7. เมื่อเลือก A: สร้างและตรวจ roster ของภาคเรียนใหม่, ตั้งกำหนดการ, เปิดใช้ภาคเรียนผ่าน
   ขั้นตอนแอดมิน, แล้วเรียก `initialize_term_scores` ผ่าน workflow ที่มีสิทธิ์ตามปกติ
   (ไม่ใช่การแก้ตารางโดยตรง) เก็บผลลัพธ์และ audit ที่เกิดขึ้น
8. เมื่อเลือก B: ให้เจ้าของระบบจัดทำและทบทวนสคริปต์เฉพาะขอบเขต **หลัง** ข้อ 6 เท่านั้น
   สคริปต์ต้องเป็น transaction ที่ตรวจ row count, มีแผน archive/restore, และผ่านการทดสอบ
   บนสำเนาที่กู้คืนแล้วก่อน ห้ามใช้ `TRUNCATE ... CASCADE` หรือ bypass trigger แบบกว้าง
9. ตรวจหลังดำเนินการตามหัวข้อถัดไป แล้วเปิดการเขียนกลับเมื่อผู้อนุมัติรับรองผลเท่านั้น

## ข้อควรระวังด้าน FK และวิธีล้าง (หากเลือก B)

ความสัมพันธ์เป็นแบบ `ON DELETE RESTRICT` หลายจุด และบางตารางมี trigger immutable.
ดังนั้นการลบแบบกว้างหรือเปลี่ยนยอด `score_accounts` โดยไม่สอดคล้องกับ
`score_ledger` จะทำให้ประวัติไม่ถูกต้องหรือถูกปฏิเสธโดยฐานข้อมูล

การลบทีละตารางด้วย `DELETE` ใช้ไม่ได้อย่างปลอดภัยใน schema นี้ เพราะมีทั้ง trigger
immutable และวงจร FK ระหว่าง `appeals` กับ `paper_documents` หลัง archive และอนุมัติ
ครบแล้ว ให้ใช้ transaction ที่ล็อกช่วงบำรุงรักษาและ `TRUNCATE` แบบ **ระบุครบทั้ง 16
ตารางในคำสั่งเดียว** เท่านั้น โดยใช้ `CONTINUE IDENTITY`, ห้าม `CASCADE`, ห้ามปิด
trigger และต้องตรวจ FK closure จาก preflight ก่อนทุกครั้ง สคริปต์ปฏิบัติการที่ผ่านการ
ทบทวนคือ `supabase/operations/reset_all_trial_score_data.sql` และใช้ได้เฉพาะ `psql`
ที่เชื่อมต่อฐานข้อมูลซึ่งตรวจสอบแล้วเท่านั้น หากใช้ Supabase Management API ให้สร้าง
ไฟล์แบบคำสั่งเดียวด้วย `scripts/generate-operational-reset-query.mjs` โดยผูก database,
project, migration head, roster, backup และ restore drill ให้ตรงกับ preflight จากนั้น
ทดสอบไฟล์ที่ได้กับฐานข้อมูลสำเนาที่กู้คืนผ่าน `supabase db query --file` ก่อนใช้ไฟล์
production ผ่าน `supabase db query --linked --file` เสมอ ตัวสร้างไฟล์จะไม่เขียนทับ
ไฟล์เดิมและอนุญาตให้เก็บเฉพาะใน `private-data` หรือโฟลเดอร์สำรองภายนอก repository
ห้ามนำสคริปต์ `psql` แบบหลายคำสั่งไปใช้ผ่าน Management API/SQL Editor, ห้ามลบ
`audit_logs`, ตัวตน, roster, กฎ หรือ permissions และห้ามลบ `storage.objects` โดยตรง

## เกณฑ์ตรวจสอบผล

สำหรับทางเลือก A ให้ตรวจอย่างน้อย:

- ภาคเรียนใหม่มี enrollment ที่ active ครบตาม roster ที่อนุมัติ
- จำนวนนักเรียน active enrollment เท่ากับจำนวน `score_accounts` ของภาคเรียนใหม่
- ทุก `score_accounts.balance` ของภาคเรียนใหม่เป็น 100 หลัง initialization และมี
  `score_ledger.entry_type = 'semester_opening'` ที่สอดคล้องกัน
- ภาคเรียนเก่า, ประวัติ score ledger, audit, บัญชี, รายชื่อ, การมอบหมาย, สิทธิ์ และ
  รูปโปรไฟล์ยังอยู่ตามผล preflight ก่อนเริ่ม
- ไม่มีคำขอ/อุทธรณ์/งานติดตามค้างที่ถูกละทิ้งโดยไม่มี owner หรือสถานะที่อนุมัติ

สำหรับทางเลือก B ให้ตรวจเพิ่มว่า row counts หลังดำเนินการตรงกับ scope ที่อนุมัติ,
archive และไฟล์หลักฐานเปิดอ่าน/ตรวจ checksum ได้, FK ไม่มี orphan, และข้อมูลนอก
scope ไม่มีการเปลี่ยนแปลง ใช้ผล preflight ก่อน–หลังเป็นหลักฐาน

## Rollback

อย่าพยายามย้อนกลับด้วยการเขียนยอดหรือสร้าง ledger เดาเอง หากพบความคลาดเคลื่อน:

1. คงช่วงหยุดเขียนไว้และบันทึกเวลา/ผู้ปฏิบัติ/ข้อความผิดพลาด
2. หยุดงานที่ทำซ้ำได้และห้ามมีการ reset เพิ่ม
3. กู้คืนจาก backup/snapshot ที่ตรวจสอบแล้วไปยังสภาพแวดล้อมแยกก่อน แล้วตรวจ
   row count, FK, audit และข้อมูลตัวอย่าง
4. ให้ผู้รับผิดชอบอนุมัติแผนกู้คืนก่อนดำเนินการกับ production; ระบุ recovery point
   และผลกระทบต่อข้อมูลที่เกิดหลัง backup อย่างชัดเจน
5. หลัง restore ให้รัน preflight ซ้ำและบันทึกผลใน ticket ก่อนเปิดระบบเขียนกลับ

## สิ่งที่เอกสารนี้ตั้งใจไม่ทำ

- ไม่เชื่อมต่อ Supabase จริง ไม่ลบข้อมูล และไม่ deploy
- ไม่ใช้ `DELETE` ทีละตาราง, `TRUNCATE ... CASCADE`, การแก้ยอดคะแนนด้วย `UPDATE`
  หรือการปิด trigger; การล้างที่อนุมัติใช้เฉพาะสคริปต์แบบระบุ FK closure ครบถ้วน
- ไม่ลบ `auth.users` หรือ storage bucket ใด ๆ
- ไม่สร้างสคริปต์ destructive จนกว่าจะระบุ retention scope และผ่านจุดยืนยันข้างต้น
